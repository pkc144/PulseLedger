# v1.2.0 release verification

What was run to verify `v1.2.0` (`7c7b958`), and what it produced. Every result below is from a real
run on 2026-08-19. The decisions are recorded in
[ADR-006](../adr/006-retention-boundaries-and-operator-replay.md); this is the evidence.

**Environment:** Darwin 24.6.0 (x86_64, 12 CPUs, 32 GiB), Node.js 22.23.1, npm 10.9.8, Docker
Desktop, PostgreSQL 17.10 (`postgres:17-alpine`, limited to 2 CPU / 2 GiB by `compose.yaml`).

## What this release adds

Three operator-facing capabilities, all outside the request path, all acting only on terminal state:
dead-letter inspection and replay, retention sweeps with explicit per-table boundaries, and a
Prometheus metrics endpoint. The ledger's transaction path — posting, transfers, idempotency,
outbox writes, the consumer — is **unchanged** from `v1.1.0`.

### New tests

`tests/integration/operations.integration.test.ts` (14 cases) and `tests/unit/metrics.test.ts` (4).
The ones carrying the decisions:

| Claim                                            | Test                                                                                    |
| ------------------------------------------------ | --------------------------------------------------------------------------------------- |
| Only exhausted events are listed as parked       | _lists only events parked after exhausting their attempts_                              |
| Replay restores the budget and keeps the error   | _returns a parked event to the queue with a fresh attempt budget_                       |
| The worker's own rows cannot be replayed         | _refuses to replay an event the worker still owns_                                      |
| Replay actually re-enters the claim query        | _makes a replayed event claimable again by the worker_                                  |
| Retention never touches undelivered work         | _deletes processed outbox events past the cutoff and keeps everything else_             |
| An in-progress claim survives any age            | _deletes completed idempotency records past the cutoff but never in-progress ones_      |
| Batching loses no rows                           | _sweeps in batches without missing rows_                                                |
| **The dedup boundary cannot be swept**           | _never sweeps the dedup boundary or the audit trail_ (asserts the `DELETE` is rejected) |
| `/metrics` is admin-only, not customer-reachable | _requires the admin key_ · _is not reachable with a customer key_                       |
| Text and JSON metrics agree                      | _reports the same transfer numbers as the JSON endpoint_                                |

## Benchmarks: deliberately not re-run

The [v1.1.0 numbers](./v1.1.0.md#benchmarks) stand as the current measurement. Nothing in this
release touches the transfer path: no change to posting, locking, retries, idempotency, or the
outbox write. What changed is one added admin-guarded route and two CLIs that do not run during a
scenario — and `/v1/admin/metrics`, the JSON endpoint the k6 scenarios read, is untouched.

Re-running four scenarios to produce numbers that differ only by this machine's documented
run-to-run noise would manufacture a comparison, not measure one. The
[environment note in RESULTS.md](../../benchmarks/k6/RESULTS.md) explains why that noise is larger
than any effect this release could have.

## Bug found while building this

`timestamptz 'infinity'` — how a parked event records "no next attempt" — arrives from `pg` as the
JS number `Infinity`, not a `Date`, so mapping such a row threw `row.next_attempt_at?.toISOString is
not a function`. It was latent: the worker's claim query filters `next_attempt_at <= now()`, which
infinity never satisfies, so no existing code path had ever selected one of these rows. The new
listing did, and the test caught it on its first run. Fixed in `toNextAttempt`, which renders
infinity as the string `'infinity'` so `outbox show` tells the truth about the row.

## One flake worth recording

The suite now starts **10 Testcontainers in parallel**, one per integration file. A single local run
failed in `beforeAll` at container startup, immediately after a Docker daemon restart; three
subsequent local runs and the CI run all passed. No concurrency cap was added on the strength of one
observation in a degraded environment — but if CI starts flaking, bounding `poolOptions.forks` is
the first thing to try.
