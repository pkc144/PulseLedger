# v1.2.1 release verification

A documentation-and-configuration patch. **No application logic changed** — `src/` differs from
`v1.2.0` only in that entrypoints now load `.env` when one exists, and `migrations/`, `tests/`, and
`benchmarks/` are untouched. Every measurement in the [`v1.2.0` record](./v1.2.0.md) still describes
this release.

## Why this release exists

The README quick start did not work as written. The project has no dotenv dependency and no script
passed `--env-file`, so the documented sequence:

```bash
cp .env.example .env
npm ci
docker compose up -d postgres
npm run db:migrate
```

failed on the last step with `DATABASE_URL is required`. Anyone following the README — the exact
audience the README exists for — hit an error on step four and had to guess that the variables
needed exporting.

**Why the earlier clean-clone checks missed it.** The verification scripts behind the `v1.0.0`,
`v1.1.0`, and `v1.2.0` records each did `export DATABASE_URL=... ADMIN_API_KEY=...` before running
anything. They proved the _steps_ work; they never exercised the _documented environment handling_,
because they helpfully supplied what a reader would not have. A check that fills in the reader's
missing context is not checking the reader's experience.

## The fix

Every entrypoint script now passes `--env-file-if-exists=.env`:

| Script                             | Loads `.env` |
| ---------------------------------- | ------------ |
| `dev`, `start`                     | yes          |
| `db:migrate`, `seed`               | yes          |
| `reconcile`, `outbox`, `retention` | yes          |

`engines.node` is raised to `>=22.9.0`, the release where `--env-file-if-exists` landed. Real
environment variables still take precedence over the file, which is how Docker and CI supply
configuration — nothing about the container or the workflow changes.

## Verification

The quick start run **literally**: fresh clone, `.env` copied from `.env.example`, and **nothing
exported** at any point.

```text
$ git clone <repo> && cd PulseLedger
$ cp .env.example .env          # edited only to point at a throwaway database and set a key
$ npm ci                        → ok
$ npm run db:migrate            → Database migrations completed
$ npm run build                 → dist/ produced
$ npm start
  health/ready                  → {"status":"ready","outbox":{"pending":0,"processing":0,"failed":0}}

  create principal + issue key  → ok  (pl_live_TYIU0KnQ...)
  fund 250000                   → 201
  transfer 75000                → 201, idempotency-key: my-first-transfer
  npm run reconcile             → 4 accounts checked, 0 issues
  npm run outbox list           → no parked events
  npm run retention -- --dry-run → both retention windows reported
```

`PORT` was set in that `.env` too, and the server honoured it — which is the same mechanism proving
the file is read rather than the shell.

## Also in this release

project solves and what goes wrong without each, the evidence in one glance, and a copy-paste demo —
so a non-specialist reader can understand it in a minute. The engineering material is unchanged and
now sits under "For engineers".
