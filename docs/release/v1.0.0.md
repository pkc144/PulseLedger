## CI status

**The `v1.0.0` tag points at a commit whose CI run is red, and this document originally claimed
otherwise.** The claim was made from the workflow definition rather than from run history; the run
history shows `npm test` failing on every push since Week 5. The tag is left where it is rather than
quietly moved, and this section is the correction.

The failure was in the CI configuration, not the product. `.github/workflows/ci.yml` exported
`TEST_DATABASE_URL` pointing every integration test file at one shared database. Each file runs the
migrations itself and assumes it owns its data, and vitest runs the files in parallel, so they
deadlocked on concurrent DDL (`40P01`, `AccessExclusiveLock on relation`) and read each other's rows
(`expected 409 to be 201`, `expected [409, 409] to deeply equal [201, 409]`, wrong entry counts).

Reproduced locally, both directions:

```text
TEST_DATABASE_URL=<one shared db> npm run test:integration   → 29 failures
npm test  (Testcontainers, one database per file)            → 126 passed
```

Fixed by removing `TEST_DATABASE_URL` from the workflow so CI uses Testcontainers per file, exactly
as a local run does. Everything else in this document was verified locally and stands unchanged; the
tagged code is identical to the code that produced every other result here.

## Benchmark re-verification

All four k6 scenarios were re-run on the release commit against a freshly seeded database (300
accounts, 3,000 transfers). Raw stdout and summary JSON:
[`benchmarks/k6/results/release-v1.0.0/`](../../benchmarks/k6/results/release-v1.0.0/).

| Scenario                 | Requests | Throughput  | p50      | p95      | `http_req_failed` | Retry-exhausted |
| ------------------------ | -------- | ----------- | -------- | -------- | ----------------- | --------------- |
| `normal-transfer`        | 2,940    | 95.0 req/s  | 30.8 ms  | 471.8 ms | 7.00% (206)       | 206             |
| `duplicate-storm`        | 55       | 1054 req/s  | 18.2 ms  | 24.0 ms  | 0.00% (0)         | —               |
| `hot-account-contention` | 2,868    | 141.5 req/s | 133.6 ms | 426.9 ms | 25.13% (721)      | 721             |
| `broad-concurrency`      | 6,190    | 118.9 req/s | 269.2 ms | 1620 ms  | 4.15% (257)       | 257             |

- `duplicate-storm` moved the completed-transfer counter by **exactly 1** across 50 concurrent
  identical requests.
- In every contention scenario the failed-request count equals the `TRANSFER_RETRY_EXHAUSTED` delta
  exactly — the only non-2xx responses are the bounded-retry path.
- After 11,184 transfer attempts (10,000 completed, 1,184 exhausted):
  `npm run reconcile` → `{ "accountsChecked": 719, "issues": [], "ok": true }`.

Latency and failure percentages differ from the canonical Week 7 run in both directions; that
variance and its cause are documented in
[benchmarks/k6/RESULTS.md](../../benchmarks/k6/RESULTS.md#release-re-verification-v100).

## Documentation verification

Every documented claim was checked against the implementation, not against an earlier draft.

- **API reference.** Every request/response pair in [docs/API.md](../API.md) was captured from a
  running server, including all failure modes: `401 UNAUTHORIZED` (missing and wrong key),
  `400 VALIDATION_ERROR`, `400 SELF_TRANSFER`, `400 CURRENCY_MISMATCH`, `400 INVALID_AMOUNT`,
  `400 INVALID_CURSOR`, `404 ACCOUNT_NOT_FOUND`, `404 TRANSFER_NOT_FOUND`, `404 ROUTE_NOT_FOUND`,
  `409 INSUFFICIENT_FUNDS`, `409 IDEMPOTENCY_CONFLICT`, and `413 REQUEST_REJECTED`.
- **Diagrams.** Table and column names in the data-model diagram were checked against
  `migrations/001`–`008`; the module-dependency diagram matches the rules in
  `scripts/check-architecture.ts`; the transfer sequence matches
  `transfer-service.ts` / `transfer-repository.ts` statement for statement.
- **Corrections made during verification.** ADR-003 described the outbox worker as a "separate
  process", which contradicted ADR-004 and the code (it is an in-process loop) — corrected. ADR-002's
  forward-looking note about idempotency now carries an update section with the measured outcome.
  The README still described the repository as being at Week 4 — replaced.

## Résumé bullet

Measured results only; every number appears in this repository.

> **PulseLedger — double-entry payment ledger (TypeScript, Fastify, PostgreSQL).** Built a
> correctness-first ledger holding four financial invariants under real concurrency: `SERIALIZABLE`
> transfers with deterministic lock ordering and a bounded 12-attempt retry budget, an idempotency-key
> contract that collapsed **50 concurrent identical requests into exactly one posting**, and a
> transactional outbox plus consumer inbox that turned at-least-once delivery into **one effect across
> 1,000 duplicate deliveries**. Verified with **126 automated tests** (unit, property, integration,
> concurrency, crash-recovery) and four k6 load scenarios: **~14,000 transfer attempts, zero
> overdrafts, and zero balance drift across 763 accounts** — with degradation confined to bounded
> `503`s under deliberate hot-account contention.

Shorter variant for a one-line résumé:

> Built a double-entry payment ledger (TypeScript/Fastify/PostgreSQL) that survived ~14,000
> concurrent transfer attempts with zero overdrafts and zero balance drift, using `SERIALIZABLE`
> transactions with bounded retries, idempotency keys (50 concurrent duplicates → 1 posting), and a
> transactional outbox with an idempotent consumer (1,000 duplicate deliveries → 1 effect); 126
> automated tests.
