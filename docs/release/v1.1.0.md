# v1.1.0 release verification

What was run to verify `v1.1.0` (`528bf44`), and what it produced. Every result below is from a real
run on 2026-08-17. The feature itself is described in
[ADR-005](../adr/005-api-key-authentication-account-ownership.md); this is the evidence.

**Environment:** Darwin 24.6.0 (x86_64, 12 CPUs, 32 GiB), Node.js 22.23.1, npm 10.9.8, Docker
Desktop, PostgreSQL 17.10 (`postgres:17-alpine`, limited to 2 CPU / 2 GiB by `compose.yaml`),
k6 v2.2.0.

## What changed, and what that means for the earlier record

`v1.1.0` adds authentication and authorization to the customer API. The ledger mechanics —
double-entry posting, `SERIALIZABLE` transfers, bounded retries, the outbox, the consumer inbox,
reconciliation — are untouched, so the invariant evidence in
[v1.0.0's record](./v1.0.0.md) still holds. Two things about it are now **stale** and are superseded
here:

- Its test counts (126) — the suite is now **151**.
- Its "Customer routes are unauthenticated" caveat, which is exactly what this release removes.

## Benchmarks

All four scenarios re-run on this tag against a freshly seeded database (300 accounts / 3,000
transfers, seeded through the real services). Raw stdout and summary JSON:
[`benchmarks/k6/results/release-v1.1.0/`](../../benchmarks/k6/results/release-v1.1.0/).

| Scenario                 | Requests | Throughput  | p50      | p95      | `http_req_failed` | Retry-exhausted |
| ------------------------ | -------- | ----------- | -------- | -------- | ----------------- | --------------- |
| `normal-transfer`        | 2,498    | 79.4 req/s  | 49.4 ms  | 560.3 ms | 9.24% (231)       | 231             |
| `duplicate-storm`        | 57       | 924 req/s   | 23.3 ms  | 32.8 ms  | 0.00% (0)         | —               |
| `hot-account-contention` | 2,803    | 138.3 req/s | 144.9 ms | 430.4 ms | 24.79% (695)      | 695             |
| `broad-concurrency`      | 2,888    | 55.2 req/s  | 541.5 ms | 2920 ms  | 17.10% (494)      | 494             |

Every scenario now provisions its own principal and API key in `setup()` and sends a bearer token on
every customer request — which is why `duplicate-storm` shows 57 requests rather than 55.

What held:

- **`duplicate-storm` moved the completed-transfer counter by exactly 1** across 50 concurrent
  identical requests, now with authentication on the path.
- Every contention scenario's `http_req_failed` count equals its `TRANSFER_RETRY_EXHAUSTED` delta
  exactly (231/231, 695/695, 494/494) — the only non-2xx responses are still the bounded-retry path,
  and authentication adds no new failure mode under load.
- `hot-account-contention` verified over HTTP in `teardown()` that every hot account ended
  non-negative and exactly conserved.
- After 7,369 transfer attempts (5,949 completed, 1,420 exhausted):
  `npm run reconcile` → `{ "accountsChecked": 707, "issues": [], "ok": true }`.

**On the cost of authentication:** each request now does one extra indexed read plus a SHA-256
digest. This environment cannot measure that. The same four scenarios on the same machine already
varied by more than 2× between two `v1.0.0` runs (`broad-concurrency` failed 16.92% then 4.15%), so
the differences here sit inside noise that dwarfs a single indexed lookup, and attributing them to
the guard would be a fabricated number. Isolating it would need a dedicated rig, a warmed cache, and
repeated runs — which is a different exercise than this project's benchmarks are for. See the
environment note in [RESULTS.md](../../benchmarks/k6/RESULTS.md).

## Two findings from building this

Both were caught by tests rather than review, and both are fixed in this release:

1. **The guards ran after body validation.** Fastify validates the body before `preHandler`, so an
   anonymous caller received `400` schema feedback instead of `401` and could map request shapes
   with no credential. Both guards moved to `onRequest`; a regression test pins the ordering.
2. **Idempotency keys were globally scoped.** A test written for cross-principal isolation failed,
   proving that two callers choosing `order-42` would collide — and that one could see the other's
   stored response. The unique index is now `(principal_id, key, operation)`.

## Résumé bullet

Measured results only; every number appears in this repository.

> **PulseLedger — double-entry payment ledger (TypeScript, Fastify, PostgreSQL).** Built a
> correctness-first ledger holding its invariants under real concurrency: `SERIALIZABLE` transfers
> with deterministic lock ordering and a bounded 12-attempt retry budget, an idempotency-key contract
> that collapsed **50 concurrent identical requests into exactly one posting**, and a transactional
> outbox plus consumer inbox that turned at-least-once delivery into **one effect across 1,000
> duplicate deliveries**. Added hashed API-key authentication with account ownership enforced by
> database constraint and validated **inside the transfer's locked transaction**, so authorization
> cannot be raced. Verified with **151 automated tests** and four k6 load scenarios — thousands of
> concurrent transfer attempts with **zero overdrafts and zero balance drift**, degradation confined
> to bounded `503`s.
